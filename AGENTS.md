# AGENTS.md

## Project

**Name:** `imgw-merge-weather`

`imgw-merge-weather` is a self-hosted homelab application for collecting IMGW CMM MERGE precipitation forecast imagery, exploring forecast frames in a browser, and generating shareable MP4 forecast animations.

Primary deployment target:

- Linux homelab server
- Docker Compose
- single-container production deployment
- no cloud dependencies
- no API key required for IMGW imagery

The application is weather-data-first. The browser UI is not merely an admin panel for video jobs; it should evolve into a useful meteorological forecast viewer.

---

## Core Product Goals

The application should:

1. discover the latest available IMGW CMM MERGE forecast cycle,
2. construct and download MERGE JPEG frames,
3. validate every downloaded frame,
4. expose forecast runs and individual forecast timestamps to the frontend,
5. let users inspect forecast frames interactively,
6. generate MP4 animations with FFmpeg,
7. retain recent runs and generated videos,
8. optionally refresh automatically as IMGW publishes new data,
9. remain lightweight and easy to operate on a homelab.

---

## IMGW Data Source

Current known frame URL pattern:

```text
https://cmm.imgw.pl/wp-content/uploads/production/MERGE/MERGE_MERGE_10_YYYY-MM-DD_HH_MM_SS.jpg
```

Example:

```text
https://cmm.imgw.pl/wp-content/uploads/production/MERGE/MERGE_MERGE_10_2026-08-29_12_50_00.jpg
```

Filename pattern:

```text
MERGE_MERGE_10_{timestamp}.jpg
```

Timestamp format:

```text
%Y-%m-%d_%H_%M_%S
```

MERGE characteristics:

- forecast horizon: approximately 8 hours,
- forecast step: 10 minutes,
- update cadence: approximately every 10 minutes,
- spatial resolution: approximately 1 km,
- precipitation forecast product generated by IMGW CMM.

Treat the remote service as a third-party dependency.

Do not attempt to bypass access controls, WAF rules, CAPTCHAs, authentication, or other restrictions.

## Time Handling

This project must distinguish between:

- IMGW/CMM timestamp convention,
- internal canonical timestamps,
- local display timestamps.

Use timezone-aware datetimes everywhere.

### Internal representation

Prefer UTC internally.

Example:

```text
2026-08-29T08:20:00Z
```

### UI representation

Display local time in:

```text
Europe/Warsaw
```

Example:

```text
29.08.2026 10:20
```

The CMM nowcasting UI labels weather times as UTC. Verify the actual filename convention against live requests before hard-coding assumptions.

Never mix naive Python datetimes with timezone-aware datetimes.

## Core Domain Concepts

Do not model everything as a generic “job”.

The application has several distinct concepts.

### Forecast Run

A snapshot of the available MERGE forecast collected at a given ingestion time.

A run includes:

- ID,
- discovery timestamp,
- source/product,
- resolved starting forecast time,
- final forecast time,
- interval,
- expected number of frames,
- downloaded number of frames,
- status,
- freshness,
- manifest,
- individual frames.

### Forecast Frame

A single remote IMGW image corresponding to one forecast timestamp.

Fields should include:

- run ID,
- frame index,
- forecast timestamp,
- source URL,
- local filename,
- dimensions,
- hash if useful,
- validation status.

### Video Generation

An artifact generated from one forecast run.

It has its own lifecycle:

```text
pending
rendering
completed
failed
```

A forecast run may produce multiple videos:

```text
source
1:1
16:9
9:16
```

Do not force a one-run-one-video model.

## IMGW HTTP Client Rules

Use a dedicated client abstraction, e.g.:

```python
ImgwMergeClient
```

Use:

```python
httpx.AsyncClient
```

Recommended headers:

```text
User-Agent: imgw-merge-weather/1.0 homelab-weather-viewer
Accept: image/avif,image/webp,image/apng,image/jpeg,*/*
Referer: https://cmm.imgw.pl/
```

Default concurrency should remain conservative:

```text
4
```

Implement:

- connection timeout,
- read timeout,
- retries,
- exponential backoff,
- bounded concurrency,
- informative logging.

Do not aggressively poll IMGW.

Do not use `HEAD` as the only availability signal.

Use GET and validate the response body.

---

## Frame Validation

HTTP 200 does not imply a valid weather frame.

Validate:

- response status,
- response body size,
- image MIME type where available,
- Pillow can decode the file,
- Pillow `verify()` succeeds,
- dimensions are sensible.

Reject:

- HTML error responses,
- zero-byte files,
- truncated JPEGs,
- suspiciously tiny bodies.

Write files atomically:

```text
file.tmp
→
file.jpg
```

Never leave partial frames under the final filename.

## Forecast Sequence Logic

Default:

```text
FRAME_INTERVAL_MINUTES=10
FORECAST_HOURS=8
```

Eight hours inclusive of the starting frame:

```text
49 frames
```

Required helpers:

```python
floor_to_interval()
build_frame_times()
build_frame_url()
```

The application must support:

- latest available forecast,
- explicit forecast start,
- fallback when the newest cycle is not yet published.

Default fallback:

```text
MAX_START_FALLBACK_STEPS=6
```

Fallback applies only to locating a valid starting cycle.

Do not silently shift individual missing timestamps after the run has started.

---

## Refresh Strategy

MERGE is expected to update roughly every 10 minutes.

Recommended scheduler behavior:

```text
02,12,22,32,42,52 minutes past the hour
```

This provides a small delay after expected IMGW publication.

Example:

```cron
2,12,22,32,42,52 * * * *
```

Recommended flow:

```text
expected publication
→ small delay
→ probe newest run
→ retry if not yet available
→ ingest complete run
→ mark latest
→ optionally generate video
```

Avoid generating duplicate runs when the newest remote data is unchanged.

Do not permanently cache a frame solely by forecast timestamp if a later MERGE publication can revise the forecast for that same future timestamp.

Cache should be scoped to forecast runs.

## Missing Frame Policy

Default:

```text
ALLOW_MISSING_FRAMES=false
```

Strict mode:

- fail ingestion or video generation if required frames are unavailable,
- report exact missing forecast timestamps.

Optional permissive mode:

```text
ALLOW_MISSING_FRAMES=true
MIN_FRAME_COVERAGE=0.90
```

If enabled:

- preserve chronological order,
- skip unavailable timestamps,
- enforce minimum coverage.

Never duplicate an old frame and label it as a missing forecast timestamp.

## Video Generation

Use FFmpeg as a subprocess.

Do not use OpenCV for encoding.

Defaults:

```text
VIDEO_FPS=5
VIDEO_CODEC=libx264
VIDEO_CRF=20
VIDEO_PRESET=medium
```

Output:

```text
H.264
yuv420p
MP4
```

Use ffprobe after generation.

Validate:

- video stream exists,
- codec is H.264,
- duration > 0,
- dimensions are expected,
- output file size is sensible.

Do not mark generation complete solely because FFmpeg returned exit code 0.

## Frontend Product Philosophy

This is not primarily an admin CRUD dashboard.

The primary user intent is:

```text
“What does the latest precipitation forecast look like?”
```

Therefore:

- weather imagery should dominate the screen,
- latest forecast should be available immediately,
- interactive timeline should be central,
- metadata should be compact,
- generation controls should be secondary.

The long-term web experience should be more useful than the MP4.

## Background Work

Long-running HTTP requests must not block API responses.

Do not add Redis/Celery for the initial application.

Use a lightweight internal background-job mechanism.

Prevent duplicate execution.

On startup:

- detect interrupted operations,
- mark or recover them explicitly,
- never leave jobs permanently stuck in `running`.

Scheduling is optional.


Recommended production:

```text
SCHEDULER_ENABLED=true
SCHEDULER_CRON=2,12,22,32,42,52 * * * *
```

If a previous scheduled refresh is still running:

```text

```

and log the event.

## Retention

Suggested defaults:

```text
OUTPUT_RETENTION_DAYS=7
FRAME_RETENTION_HOURS=24
```

However, be careful with frame retention if the frontend is expected to browse historical runs.

Retention policy should eventually support:

- keep latest N runs fully,
- keep generated videos longer,
- retain one hourly snapshot longer than every 10-minute run,
- prune old raw frames.

Never delete outside the configured data directory.

Validate filesystem paths.

## Storage Expectations

A typical 1080×1080, 5 FPS, H.264 MERGE animation is expected to be only a few MB.

Approximate working assumption:

```text
2–4 MB per generated video
```

At a 10-minute generation cadence:

```text
144 videos/day
```

Therefore retention must be deliberate.

Do not use these estimates as exact limits.

## Security

Never:

- accept arbitrary source URLs from API users,
- allow arbitrary FFmpeg arguments,
- allow directory traversal,
- expose filesystem paths blindly,
- use unbounded concurrency,
- trust output filenames from client input.

Validate:

- forecast horizon,
- FPS,
- video mode,
- resolution,
- run ID,
- frame index.

Basic Auth may be added for simple remote homelab access.

Do not build a full user-account system initially.

Recommend:

- Tailscale,
- Caddy,
- Traefik,
- Nginx

for remote access.
